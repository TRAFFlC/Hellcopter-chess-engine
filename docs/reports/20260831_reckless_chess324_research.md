## 1. 先回答隐含的前提问题：Chess324 是什么

用户说"Reckless 支持 chess324"。在分析 Reckless 之前必须先把 chess324 钉死（这对理解后文至关重要）：

**Chess324（Larry Kaufman, 2022-08）[1][2]：**

- 王与车固定在标准位置（e1/e8、a1/h1/a8/h8）；
- 其余 5 子（后、双马、双象）随机排在 b1,c1,d1,f1,g1（及黑方对应列）；
- **双方独立随机，无对称要求**（这是它与 Chess960 的本质区别——它是 DFRC/双面独立随机的子集）；
- 唯一约束：每方双象异色格 → 每方 18 种排列 → 18×18=**324 种局面**；
- **易位规则完全标准**——王车都在老家，所以"不需要任何特殊易位规则，任何引擎、GUI 或人类看到初始局面就能直接下"（Kaufman 原文 [1]）；
- 发明动机：减少引擎对弈的和棋率（324 局面绝大多数不对称，天然打破平衡）。

**两个立刻可下的推论：**

1. **"支持 chess324"的门槛极低**：不需要改易位逻辑、不需要新模式——只要引擎的 FEN 解析器能接受任意合法起始排列，它就能下 chess324。Hellcopter 的 FEN 解析器（如果健壮）大概率"能下"。
2. **Reckless 代码库中没有任何 chess324 专门代码**——全库检索 `324|960|variant`，命中的只有 `UCI_Chess960` 选项声明、Chess960 perft 测试、以及一个与变体无关的 `value.clamp(-144, 324)` 常数。

**那用户"看到 Reckless 支持 chess324"的印象从哪来？** 最可能的来源是 SPCC：Reckless 的 3833 分评级来自 SPCC（README.md:21,42），而 SPCC（Stefan Pohl 运营的评级体系）的 AntiDraw 开局集 2.0 明确包含 **Chess324 64x** 开局集（其 TalkChess 发布帖 [2]），用于降低引擎对局的和棋率。也就是说：**Reckless 的顶尖评级本身就是在包含 chess324 局面的测试池里打出来的**——它对 chess324 的"支持"是实战支持，不是接口支持。

## 2. Reckless 的变体兼容架构：三层解耦（源码实证）

回答"它是怎么做到的"：**不是单独优化，而是架构本身就把"标准开局"从所有关键路径上移除了**。分三层。

### 2.1 第一层：易位几何完全参数化（棋盘层）

Reckless 的 Board 把易位所需的一切几何信息做成**逐局面动态计算的预计算表**（board.rs:51-54）：

```rust
// board.rs:51-55（字段声明，结构描述非代码复制）
castling_rights: [u8; Square::NUM],     // 每格离开时吊销哪些权
castling_path:   [Bitboard; 16],        // 王与车易位途经+占用的空格集合
castling_threat: [Bitboard; 16],        // 王易位全程（含起终点）不能被攻击的格
castling_rooks:  [Square; 16],          // 每种易位对应的车起始格
frc: bool,
```

这四张表在 FEN 解析时由 `set_castling()` 一次性填好（parser.rs:68-116）。填表逻辑是纯几何的：

- 接受**Shredder-FEN（A-H/a-h 文件字母）**与标准 KQkq 两种易位标记：`right.to_ascii_uppercase()` 匹配 `'A'..='H' | 'K' | 'Q'`（parser.rs:70）；
- 对 K/Q：从**王当前实际位置**出发向左/右扫射线找第一个己方车（parser.rs:76-86）——**不假设王在 e1、车在 h1/a1**；
- 对 A-H：字母与王位的差值直接给出扫描方向（parser.rs:76）；
- 王的落地格固定 G1/C1、车的落地格固定 F1/D1（castling.rs:18-25 的 `landing_square()`、parser.rs:92-93 的 `KING_TO_FILE/ROOK_TO_FILE`），**但王车的起始格完全任意**；
- `castling_path = 王 from→王 to 途经 ∪ 王 to ∪ 车 from→车 to 途经 ∪ 车 to`，再剔除两个起始格（parser.rs:107-111）——任意起始排列下王与车可能同翼交错（如王 g1 车 h1 的 960 短易位王不移动），路径表达式自动覆盖所有情况；
- `castling_threat = 王 from→王 to 的全程含端点`（parser.rs:113）。

**搜索与走法生成因此变成纯查表**（movegen.rs:93-104）：易位合法 ⇔ 权存在 ∧ path 空着 ∧ threat 无敌火 ∧ 车未被钉。执行与回退同样只查 `get_castling_rook(to)` 拿动态车格（makemove.rs:50-60, 132-136）。

**标准国际象棋在这套机制下只是"王恰好 e1、车恰好 h1/a1"的特例。**960/324/DFRC/标准棋走的是同一份代码，零分支。

### 2.2 第二层：I/O 协议双形态（接口层）

`UCI_Chess960` 选项（uci.rs:159, 313-317）**只控制 I/O 格式，不改变任何内部逻辑**：

- 置 true：易位输出为"王吃车"形态（`e1h1`，moves.rs:132-138：`format!("{king_from}{rook_from}")`），FEN 的易位字段输出 Shredder 文件字母（castling.rs:75-82）；
- 置 false：易位输出标准 `e1g1` 形态，FEN 输出 KQkq；
- **无论开关如何，输入侧两种格式都接受**（parser.rs:70 的字符匹配不区分模式；tests.rs:50-52 用 Shredder-FEN `w HFhf - 2 9` 做 perft 验证，tests.rs:57 注释明言这是为了匹配 UCI_Chess960 模式的 FEN 输出）；
- 收到 UCI 着法时的验证方式是"生成全部合法着法，比对字符串"（uci.rs:279-286 的 `make_uci_move`）——天然免疫"易位编码形态不一致"问题。

**对 chess324 而言这一层甚至不激活**：王车在标准位 → GUI 发标准 KQkq FEN、标准 e1g1 着法 → `UCI_Chess960=false` 全程工作。

### 2.3 第三层：评估与开局先验彻底解耦（评估层——本报告核心）

Reckless **没有 PST**。`src/evaluation.rs` 全文 13 行，只是对 NNUE 原始输出的位置无关校正（材料占比、乐观系数、五十步衰减，evaluation.rs:3-13）。整条评估链上没有任何一项知道"标准开局长什么样"：

**（a）PSQ 特征是"王位置条件化"的（psq.rs:204-211）**

NNUE 第一层输入特征的索引公式（结构描述）：

```
index = KING_BUCKET[王的格子] × 768        // 10 个王桶（nnue.rs:102-111）
      + 384 × (子色 ≠ POV)                // 视角方/对方
      + 64 × 子类型 + (格子 ^ 翼翻转)      // 翼翻转 = 王在哪翼决定左右镜像（psq.rs:205）
```

王桶布局（nnue.rs:102-111）值得逐行读：第 1 行王位分 8 个精细桶（王翼/后翼 × 内外侧），第 2 行 8 桶，第 3 行 1 桶，第 4-8 行共用 1 个压缩桶。这个布局本身就是"王在宫内（精细区分易位目标区）/王离开宫/王深入残局战场"的三态建模。

**这正是传统 PST 与 Reckless 特征的本质区别**：Hellcopter 的 PST 说"马在 f3 值 +X"——这句话隐含了"王在 e1/g1、棋局围绕中心展开"的标准开局先验。Reckless 的特征说"**当王在 b1 时**，己方马在 f3 值多少"——**位置价值是王位置的函数，不是绝对坐标的函数**。chess324 起始局面里王在 e1（恰好标准），但周围子力排布完全陌生；中局王可能被迫走 b1/c1——传统 PST 在这里开始失真，王桶特征在这里只是换一个桶。

**（b）威胁特征是"攻击关系"而非"位置"（threat_index.rs:103-117）**

第二组输入特征（66864 维，nnue.rs:358）索引的是"**哪个子从哪格攻击哪个子的哪格**"——`(攻击子, 攻击格, 被攻击子, 被攻击格, 是否翼镜像, POV)` 六元组。攻击关系天然与起始排列无关：b1 的马攻击 c3 在任何变体里都是同一个事实。其中还有"同型互斥/半互斥"的工程细节（threat_index.rs:84-86：同型攻击对排除兵），说明这组特征被认真设计过攻击语义的完备性。

**（c）增量维护对易位同样通用（psq.rs:114-121）**

NNUE accumulator 的增量更新里，易位分支动态取车 from/to：`board.get_castling_rook(mv.to())`——与棋盘层同一套动态几何，没有任何"车 h1→f1"的硬编码。

**（d）评估校正全部位置无关（evaluation.rs:3-13）**

材料值、五十步钟、乐观系数——按局面总数缩放，与开局形态无关。

**（e）王桶切换的工程代价已被消化（nnue.rs:242-262）**

王桶条件化的代价是：王一跨翼/跨桶，增量更新链失效，accumulator 必须全量刷新。Reckless 用 Finny-table 式的**王桶×王翼 accumulator 缓存**（psq.rs:33-67 的 `AccumulatorCache`：缓存"王在某桶某翼"状态下的全量值，下次王回到同状态直接复用）把刷新成本摊销掉。这是"解耦"能付出得起的工程前提。

## 3. 直接回答用户的三个问题

### Q1：Reckless 是单独为 chess324 做了优化吗？

**没有。**全库不存在 chess324 代码、不存在变体分支、不存在模式开关（`frc` 布尔只控 I/O 格式）。chess324 甚至是"最容易支持"的变体——王车归位使它对易位零要求。Reckless 的高棋力在 chess324 局面上成立，是因为**它的全部棋力来源（NNUE + 搜索）都不依赖标准开局假设**。

### Q2：它的能力本身兼容变体计算吗？

**是，且兼容是三层架构的自然结果**（§2）：

1. 棋盘层把易位几何参数化为逐局面预计算表——标准棋是特例而非基准；
2. 接口层双格式输入、生成着法集比对验证——不挑 GUI 编码形态；
3. 评估层特征全部以"子-格关系 + 王位置条件 + 攻击关系"表达——不存在"开局位置先验"可被违反。

### Q3：评估与 PST 是否"很大程度解耦"？

**比"很大程度"更强——是结构性解耦，而且是双重解耦：**

- **概念解耦**：传统 PST 把位置价值当作绝对坐标的函数（内嵌开局先验）；Reckless 把位置价值当作 (子, 格, **王位置桶**, 视角) 的函数（psq.rs:204-211）。后者在定义层面就不含"标准开局"这个概念。
- **功能解耦**：威胁特征（攻击关系六元组）与输出桶（按子力数分 33 档，nnue.rs:114-123）进一步把评估锚定在"结构事实"上而非"位置记忆"上。

**一个必须诚实标注的边界**：NNUE 网络本身是嵌入式二进制（nnue.rs:370-372 `include_bytes!`），**训练数据是否包含 FRC/DFRC 增强无法从源码判断**。如果只用标准对局训练，网络对 chess324 起始局面的"陌生排布"仍有分布外退化——但退化的是"对陌生局面的直觉深度"，不是"能不能算"（特征通道是完备的）。SPCC 实战评级（含 Chess324 开局集 [2]）是"实战可用"的经验证据，但"残局/中段与标准棋同强度"是推断而非实测。

## 4. 对 Hellcopter 的定向启示（不全面对比，只谈变体兼容）

按用户目标（"更全面的引擎"）排序：

1. **Hellcopter "能下" chess324 的缺口比想象小**：易位规则标准（王车归位）→ 现有易位代码无需改动；FEN 解析若已健壮则开局注入即可用。真正的差距在评估质量——PST 的开局先验在陌生排布下失真（兵 PST 的 d4/e4 峰、马 PST 的中心峰在 chess324 里依然大体成立，因为它们是"结构倾向"而非"开局记忆"；但王 PST 的 g1 谷、q1 峰这类"易位目标假设"在王被迫走 b1 时开始错位）。
2. **最低成本的解耦思想（Reckless 的王桶，思想不受 AGPL 约束）**：把 PST 索引从 `[piece][square]` 扩为 `[piece][square][king_bucket]`，王桶粗分 2-3 档（王翼/后翼/离宫）。**用现有标准开局数据调参时，"王在王翼"桶天然吸收现在的主表**，离宫桶用 Texel 从中残局数据拟合——不需要任何变体训练数据，就获得"王位置条件化"的基本形态。这是 Hellcopter 现有 Texel 管线可以直接消化的改造。
3. **兵结构/机动性/王安全特征本来就是位置无关的**（它们衡量关系而非坐标）——Hellcopter 已有的这些特征是变体兼容的存量资产，PST 才是唯一的先验污染源。这把"全面引擎"的改造面收窄到 PST 一处。
4. **易位几何动态化是低风险的正交改造**（若未来要支持 960/DFRC 类）：Reckless 的做法（解析时预计算 path/threat/rook 表，搜索只查表）表明这不必付出搜索性能代价——标准棋下预计算表与硬编码值完全一致。
5. **一个反向提醒**：AGPL v3 的传染性比 GPL 更强（网络服务条款）——Reckless 的任何代码（含 build 脚本、特征布局常量数组的具体数值）都不可进入 Hellcopter。思想层面（王桶条件化、威胁特征、动态易位几何）不受版权保护，但按 GOAL.md 纪律，落地时须在 EXPERIMENTS.md 留痕来源。

## 6. 结论（一段话）

**Reckless 对 chess324 的"支持"不存在于任何一行代码里——它存在于三层架构的不假设里**：易位几何逐局面参数化（标准棋是特例）、I/O 双格式宽容（生成着法集验证）、评估特征以"王位置条件 + 攻击关系"表达（零开局先验）。顶级引擎不是"单独为变体做了优化"，而是**把 PST 时代的"开局位置记忆"整个从架构中驱逐了**——NNUE 的王桶条件化恰好是"PST 思想的变体安全版"：它保留了"位置有价值"的全部表达力，但把价值锚定在王的位置而非棋盘的绝对坐标上。对 Hellcopter 而言，通往"全面引擎"的最短路径不是模仿 Reckless 的 NNUE，而是**给现有 PST 加上王位置条件维度**——这一个改动就能把 PST 的开局先验污染从结构性缺陷降为可调参的近似误差。
